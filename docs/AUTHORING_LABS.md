# Authoring Labs — schema v2 (`lab.yaml`)

A lab's **questions** live in `lab.yaml` inside the lab directory, next to
`metadata.json`, `check.sh` and `docker-compose.yml`. The file is the source of
truth for the question-by-question runner (per-question prompts, weights,
hints, domain breakdown). **Grading still runs the lab's `check.sh`** exactly
as before — `lab.yaml` only *describes* the questions and maps checker output
lines to them.

```
labs/<category>/<module>/<lab>/
  metadata.json     # legacy catalog metadata (still synced into the labs table)
  lab.yaml          # schema v2 — questions for the runner
  check.sh          # the grader (unchanged; runs inside the student container)
  docker-compose.yml / Dockerfile / SOLUTION.md / README.md
```

## Schema

```yaml
schema_version: 2
lab: module-01-lab-01-lost-in-the-filesystem   # must equal metadata.json id
title: Lost in the Filesystem
category: linux            # linux | kubernetes
domain: fundamentals       # default domain for the results breakdown
pass_mark: 70              # percent of total required to pass (linux 70, CKA 66)
grading_scale: percent     # percent (linux run_check weights sum to 100) | points (CKA task weights)
total: 100                 # must equal the sum of question weights
time_limit_minutes: null   # exam-mode timer; set only for mock exams (e.g. 120)
questions:
  - id: check_1                 # unique within the lab
    order: 1                    # 1..N, contiguous — the Nth check.sh output line maps to order N
    domain: fundamentals        # may override the lab domain
    weight: 35                  # percent (linux) or points (CKA) — must match check.sh
    prompt: |-                  # what the student is asked to do
      Create /home/intern/found.txt ...
    context: null               # optional extra context shown with the question
    hints:                      # 0–3, revealed in order (practice mode only)
      - title: Where to look
        content: The file is in the intern's home directory...
    solution: null              # optional per-question walkthrough (review mode only)
    explanation: null           # optional "why" note (review mode only)
    check:                      # grading contract — DO NOT hand-edit to drift from check.sh
      script: /check.sh
      index: 1                  # 1-based position of this check inside check.sh
      kind: run_check           # run_check (linux) | task (CKA)
      description: "/home/intern/found.txt exists and contains 'I navigated the filesystem'"
    time_target_minutes: 5      # optional pacing hint shown in the runner
```

## The grading contract (read this before editing)

The runner's per-question **Check** executes the same `bash /check.sh` inside
the student's container as the classic full-lab check, then maps the checker's
output lines to questions **by order**:

- linux labs emit `✅ PASS [<weight>%]: <description>` / `❌ FAIL [<weight>%]: ...` via `run_check`
- CKA labs emit `  PASS [+<pts> pts] <title>` / `  FAIL [    0] <title>` via `task` (from `check_lib.sh`)

Line *N* maps to the question with `order: N`, and `check.description` must be
byte-identical to the `run_check`/`task` description at position N — this is
how the platform proves the mapping didn't drift. If the checker ever emits a
different number of PASS/FAIL lines than there are questions, the runner
refuses to attribute results (returns the raw output unmapped, records no
per-question state) instead of guessing.

Consequences:

1. Adding/removing/reordering a question requires touching **both**
   `check.sh` and `lab.yaml` in the same change, keeping `check.index`,
   `check.kind`, `weight` and `check.description` in sync.
2. `pass_mark` must equal what `check.sh` enforces (`-ge 70` / `finish 66`).
3. `total` must equal the sum of weights.

`scripts/validate_lab_yaml.py` enforces all of the above across every lab:

```bash
python3 devops-lab-platform/scripts/validate_lab_yaml.py [--quiet] [labs_root]
```

## Creating new questions for an existing lab

1. Edit `check.sh`: add a `run_check <weight> "<description>" $?` (linux) or
   `task <pts> "<title>" '<assertion>'` (CKA) call in the right position.
2. Edit `lab.yaml`: insert the matching question at that position with the
   identical description, weight and a fresh unique `id`; renumber `order`.
3. Keep `total` / `pass_mark` consistent; run the validator.
4. Optional: fill `prompt` (student-facing), `context`, `hints`, `solution`,
   `explanation`. The `prompt` is what students see — write it as a task, not
   as the assertion.

## Regenerating lab.yaml from legacy metadata

Every current lab's `lab.yaml` was generated by the adapter from
`metadata.json` + `check.sh` (idempotent; it overwrites its own output):

```bash
python3 devops-lab-platform/scripts/migrate_labs_to_yaml.py [labs_root]
```

Migration rules: each acceptance criterion becomes one question; weight and
`check.description` come from `check.sh` (authoritative); the human criterion
description becomes the `prompt`; the lab's first 3 hints are shared by all
questions; per-question `solution`/`explanation`/`context` are left `null` for
hand authoring; `time_limit_minutes` is set only for mock-exam labs.

## Runner behavior (backend contract)

- One **attempt** per lab session (`exam_attempts`), with a persisted state
  row per question (`question_states`) — survives refresh/reload.
- Modes: `practice` (hints allowed, no timer) and `exam` (server-side timer
  from `time_limit_minutes`, hints disabled; auto-finishes at expiry).
- Per-question Check is rate-limited; results update only that question.
- **Finish** scores the attempt from the per-question states (sum of passed
  weights vs `pass_mark`% of `total`) and records a `Submission`, so XP,
  streaks, leaderboards and completion emails behave exactly like the classic
  flow. **Retry failed** starts a new attempt containing only the questions
  that did not pass.
